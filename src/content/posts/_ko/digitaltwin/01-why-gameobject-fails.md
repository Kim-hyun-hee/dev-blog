공장 하나를 화면에 띄우는 일로 시작했다. 설비 6,400개, 각각 위치와 상태와
실시간 센서 값을 가진다. 요구사항은 단순했다 — 전부 보이고, 상태에 따라
색이 바뀌고, 60fps.

첫 프로토타입은 가장 익숙한 방법으로 만들었다. 설비 하나당 GameObject 하나,
각각에 상태를 들고 있는 `MonoBehaviour` 하나. 6,400개를 인스턴스화하고
`Update()`에서 센서 값을 읽어 머티리얼 색을 바꿨다.

12fps가 나왔다.

## 프로파일러가 가리킨 곳

느리다는 것과 왜 느린지는 다른 문제다. Unity Profiler를 붙여
프레임 하나를 뜯어보니 시간이 세 군데로 갈렸다.

첫째는 `Update()` 호출 자체였다. 6,400개의 `MonoBehaviour`가 각자
`Update()`를 갖고 있으면, 엔진은 매 프레임 6,400번의 관리 코드 → 스크립트
경계를 넘나든다. 함수 본문이 비어 있어도 이 왕복 비용은 사라지지 않는다.
빈 `Update()`만 6,400개 두고 측정해도 밀리초 단위가 나온다.

둘째는 드로우콜이었다. 설비마다 머티리얼 인스턴스를 따로 만들어 색을
바꾸고 있었다. 머티리얼이 다르면 배칭이 깨지므로, 6,400개는 그대로
6,400번의 드로우콜이 됐다.

셋째가 진짜 문제였다. 상태를 읽는 코드가 캐시를 전혀 활용하지 못하고 있었다.

## 흩어진 데이터

`MonoBehaviour` 6,400개는 힙 여기저기에 흩어져 있다. 생성 순서대로 나란히
놓이리라는 보장이 없고, 각 객체 안에서 내가 실제로 읽는 건
`float temperature` 하나인데 그 옆에는 트랜스폼 참조, 렌더러 참조, 문자열
ID 같은 것들이 함께 들어 있다.

CPU는 메모리를 바이트 단위로 읽지 않는다. 캐시 라인 단위 — 보통 64바이트 —
로 끌어온다. `temperature` 4바이트를 읽으려고 64바이트를 끌어오는데, 그중
60바이트는 이번 계산에 쓰지 않는 값이다. 다음 설비의 온도는 또 다른
캐시 라인에 있다.

즉 6,400번의 순회가 사실상 6,400번의 캐시 미스다. 계산량이 문제가 아니라
데이터를 가지러 가는 왕복이 문제였다.

```csharp
// 지금 구조: 설비 하나 = 객체 하나. 필요한 값 하나를 읽으려고
// 관계없는 필드로 가득한 캐시 라인을 통째로 끌어온다.
public class Equipment : MonoBehaviour
{
    public string     id;           // 참조 8B
    public Renderer   renderer;     // 참조 8B
    public Transform  cachedTf;     // 참조 8B
    public float      temperature;  // ← 실제로 매 프레임 읽는 건 이것뿐
    public float      pressure;
    public bool       isAlarm;

    void Update()                   // × 6,400
    {
        if (temperature > threshold) renderer.material.color = Color.red;
    }
}
```

## 방향을 바꾸기로 한 이유

세 문제의 성격이 서로 달랐다.

드로우콜은 기존 구조를 유지한 채로도 줄일 수 있다. 머티리얼을 공유하고
프로퍼티 블록을 쓰거나, GPU 인스턴싱을 켜면 된다.

`Update()` 호출 비용도 마찬가지다. 매니저 하나가 배열을 들고 순회하는
방식으로 바꾸면 6,400번의 경계 왕복이 1번으로 줄어든다.

하지만 세 번째, 데이터가 흩어져 있다는 문제는 **객체마다 하나씩**이라는
전제를 유지하는 한 풀리지 않는다. 캐시를 살리려면 같은 종류의 값이
메모리에 연속으로 놓여야 하고, 그건 "설비 6,400개"가 아니라
"온도 6,400개, 압력 6,400개"로 데이터를 재배치한다는 뜻이다.

객체 중심에서 데이터 중심으로 뒤집는 것 — 데이터 지향 설계(DOD)가
말하는 게 이것이다. 다음 편에서는 Unity가 이걸 위해 제공하는 DOTS와 ECS가
정확히 무엇을 대신해주는지 정리한다.

## 이번 편 요약

- 6,400개 규모에서는 `MonoBehaviour.Update()` 호출 비용 자체가 유의미하다
- 개별 머티리얼은 배칭을 깨고 드로우콜을 그대로 객체 수만큼 만든다
- 가장 고치기 어려운 건 메모리 레이아웃이다. 객체 단위 배치를 유지하면
  캐시 미스는 구조적으로 남는다
